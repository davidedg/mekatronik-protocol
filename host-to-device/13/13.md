# `13` - Read the macro data

| bmRequestType | bRequest | wValue | wIndex | wLength |
|---|---|---|---|---|
| `c0` | `13` | `0000` | profile, `0001` to `0003` | the total length of the data, at most `1000`: see below |

Reply: the [macro data](../../formats/macro-data.md) of the profile, from its start. The vendor software does not read it.

```
27 bytes of data, asked with wLength 512:
< c0 13 0000 0001 0200
  84 04 01 87 00 03 84 04 00 87 00 26 84 05 01 87 00 01 84 05 00 86 00 01 87 00 01

5724 bytes of data (0x165c), asked with wLength 4096:
< c0 13 0000 0002 1000
  <bytes 0 to 4095 of the data, 0.5 s after the setup>
```

- **The keyboard answers min(wLength, total length)**: asked for 512 bytes, profile 1 answered its 27 bytes; asked for 100 bytes, a profile with 212 bytes answered its first 100; asked for 4096, a profile with 5724 bytes answered its first 4096 bytes, identical to what was written.
- The reply is slow, about 7 ms for each 64 bytes: 28 ms for 212 bytes, 485 to 555 ms for 4096 bytes.
- **The data of a profile with more than 4096 bytes cannot be read safely**: its first 4096 bytes are answered, but after that the next `13` hangs the keyboard (below). A tool that writes such a profile has to keep its own copy.

**Danger.** After a `13` on a profile holding more than 4096 bytes of data, the next `13` was not answered, and from then on the keyboard stalled every control request and no key worked, until it was unplugged (power cycle). [`15`](../15/15.md) sent between the two reads answered normally. Seen five times; the profiles were intact after the power cycle:

| First `13` | Its answer | Next `13` |
|---|---|---|
| profile 2, never written (index all `ff`), wLength 512 | 512 bytes of old memory content | profile 3, never written, wLength 512: no answer (3 s), hung |
| profile 2, 5724 bytes of data, wLength 4096 | its first 4096 bytes | the same profile, wValue `1000`, wLength `065c` (an offset, as [`12`](../12/12.md) writes): no answer (10 s), hung |
| the same | the same | wLength 4097: no answer (10 s), hung |
| the same, on two occasions | the same | the very same request, wLength 4096: no answer (3 s), hung |

A read that stops early on a shorter profile does not do this: profile 1 (212 bytes), asked for 100 bytes and then for 212, answered both, in two tries; asked for 212 twice in a row, it answered both.

Each of the other suspects (wValue other than `0000`, wLength above 4096, a profile that was never written) was only ever sent after such a read, so they were never tried on their own: avoid them as well.

Rules: read only a profile whose [macro index](../11/11.md) is valid and has a total length from 1 to 4096; wValue `0000`; wLength = that total. Leave the data of a longer profile unread.

Host side:

- Linux refuses synchronous control transfers above 4096 bytes (libusb and `USBDEVFS_CONTROL` give EINVAL, nothing reaches the bus).
- Under VMware Workstation (Windows 11 host), control transfers above 4096 bytes failed with a protocol error before reaching the keyboard, which did not hang.
- On a Raspberry Pi 3, `13` often failed at once with a protocol error (EPROTO, within 0.1 ms, before any data): in about half of the tries, much more often than the other requests. Asked again, it answered. After such a failure on profile 2 (5724 bytes) the next `13` answered too.

# `31` - Backlight of a zone

| bmRequestType | bRequest | wValue | wIndex | wLength |
|---|---|---|---|---|
| `40` | `31` | `pp ll` | zone, plus `80` when off | `0000` |

Sets the light of one zone. The vendor software sends four requests, one per zone, about 0.26 s apart, in the order of its settings file (`WASDLIGHT`, `DIRECTLIGHT`, `NUMBERLIGHT`, `Tt`; [vendor files](../../formats/vendor-files.md)).

| wIndex | Zone | Lit keys on the test unit |
|---|---|---|
| `0000` / `0080` | 0, WASD: on / off | W, A, S, D, left Shift, left Ctrl, Space |
| `0001` / `0081` | 1, arrows: on / off | the four arrow keys |
| `0002` / `0082` | 2, keypad: on / off | keypad 8, 4, 5, 6 |
| `0003` / `0083` | 3, Tt logo: on / off | the logo |

No other key of the test unit is ever lit (T, Y, U, the digits, ...).

For zones 0 to 2:

| wValue | Light |
|---|---|
| `0000` | level 0: dark |
| `0001` | level 1 (dimmest lit level) |
| `0002` | level 2 |
| `0003` | level 3 (brightest) |
| `0104` | pulse: the zone fades from off to full and back, about 10 s per cycle |

The low byte is the level (0 to 3, or 4 for pulse), the high byte is `01` with pulse. A zone sent with wIndex `80` + zone is off; the vendor software then sends wValue `0100` when Pulse is chosen and `0000` otherwise. In the vendor software the levels are called I to IV: its level I (`0000`) lights nothing on the test unit.

**Each zone has its own setting.** Different levels and pulse at once worked (requests sent in tests; the vendor software always sends the same value to every zone that is on): WASD level 1, arrows level 3, keypad pulse, and the other way round, each zone showed its own.

**The logo is either pulsing or off.** `0104 0003` makes it pulse (the vendor software sends this for "on", whatever the level chosen); `0000 0083` turns it off. `0000`, `0001` and `0003` with wIndex `0003` (sent in tests) left it dark.

**Global, not per profile.** A setting made on one profile stayed when another profile was selected, with [`14`](../14/14.md), with the profile keys or with an Instant Shift key, and when the work mode was changed ([`02`](../02/02.md) or the mode key). No profile write of the vendor software sends `31`.

**Not kept at power-on.** After the keyboard was unplugged and plugged back, it lit zones 0 to 2 at level 3 and the logo in pulse, whatever had been set before. A USB reset by the host most likely has the same effect *(inferred from [`04`](../04/04.md) only)*. A host program has to send the setting again each time the keyboard appears, as the vendor software does when it starts.

Seen, from the Light Option page of the vendor software ("Apply"):

| Settings | Requests (wValue wIndex) |
|---|---|
| level I, zones 0 to 2 on, logo off | `0000 0000`, `0000 0001`, `0000 0002`, `0000 0083` |
| level II, the same | `0001 0000`, `0001 0001`, `0001 0002`, `0000 0083` |
| level III, the same | `0002 0000`, `0002 0001`, `0002 0002`, `0000 0083` |
| level IV, the same | `0003 0000`, `0003 0001`, `0003 0002`, `0000 0083` |
| Pulse, the same | `0104 0000`, `0104 0001`, `0104 0002`, `0000 0083` |
| Pulse, all on, logo on | `0104 0000`, `0104 0001`, `0104 0002`, `0104 0003` |
| Pulse, only the arrows | `0100 0080`, `0104 0001`, `0100 0082`, `0000 0083` |
| Pulse, only WASD | `0104 0000`, `0100 0081`, `0100 0082`, `0000 0083` |

The software then shows the level on screen.

At start, the software sends its saved setting again, but translates Pulse differently: with `LIGHTSTYLE=0` (Pulse) it sent `0000` for the zones that are on and `0100` with wIndex `80`+zone for those that are off. With a level it sends the same as its Light Option page (`LIGHTSTYLE=1` → `0000`, `LIGHTSTYLE=4` → `0003`).

**The backlight key** sets the level of the zones that are on (sent without `80`, even at level 0): each press goes to the next level, 1, 2, 3, 4 (pulse), 0 (dark), 1, ...; zones that are off stay off, and the logo did not change (it was off). The key is [notified](../../device-to-host/81/81.md) (`fa` to `fe`); [`04`](../04/04.md) reports the levels.

**After each `31` the keyboard is busy for about 47 ms** (tests under Linux, the time counted from the completion of the previous request). A `31` sent within that time did one of two things: it waited and completed at the end of it, and was applied; or it completed 4.8 to 5.9 s later, without any error, and was **not applied** (13 times in a run with gaps of 25 ms or less; the zones 0 to 2 then still showed their old levels in [`04`](../04/04.md), a lost logo request showed only by its duration). A [`15`](../15/15.md) sent at once after a `31` was not answered within 100 ms, and an [`04`](../04/04.md) sent 0.2 s later took more than 3 s; then the keyboard answered normally. So nothing should be sent within that time, after the last `31` of a change too.

Gaps from the completion of each `31` to the next request: 260, 100 and 50 ms all worked (each `31` completed in 0.4 to 2 ms); 120 requests at 70 ms and 120 at 50 ms were all applied; with 70 ms after the last `31`, a `15` and an `04` sent right after were answered in about 5 ms. Four zones then take about 0.3 s.
